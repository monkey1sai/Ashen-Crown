# 讀者評論與創作者回應

這裡保存《灰燼之冠》的讀者閱讀經驗，讓創作者知道哪些場景有效、哪些地方造成困惑或疲勞，以及修訂後的閱讀感受有沒有改變。它與既有 `reviews/` 的文學、設定及分鏡審查並存，不是發表或合併的核准門檻。

本輪評論針對連續小說閱讀體驗；不能直接推定每日互動篇章、其他分支或分鏡也有同樣問題。評論者曾參與小說整理與插圖，因此不是完全陌生、完全獨立的盲讀者。

## 如何啟動一次評論

創作者提出閱讀範圍即可，例如：

> 請依 reviews/reader-feedback 的機制，以讀者角度評論小說第 21–24 章。先讀正文再看設定，保存評論與回應表；先不要改故事。

複讀時可以說：

> 我已依 RF-20261029-01 的 F01、F03 修訂。請讀修訂前後正文，檢查人物動機和節奏是否改善，保留原評論，另存複讀結果。

本機評論請求只啟動指定閱讀及評論文件工作；不自動授權改故事、發通知、排程、commit、push、PR 或 merge。沒有背景監看或自動執行程式。創作者可在完成一段故事、改完重點場景或需要讀者視角時主動要求，不規定固定週期。

## 輕量流程

1. **固定閱讀版本。** 記錄日期、評論 ID、作品形態、檔案、章節／day 範圍、Git 完整 SHA、未提交變更及已知參與關係。未提交稿另記正文 SHA-256；檔案 hash 必須說明是否正規化換行。不要將舊稿評語冒充最新稿結論。
2. **先讀作品。** 先記吸引、困惑、疲勞、情感轉折與期待，再按需要查設定。若設定能回答、正文不能，保留「正文尚未傳達」的閱讀感受，並標明查過的補充材料。只讀部分就明說，不推論全書。
3. **留下整體閱讀經驗。** 說明會不會繼續讀、最記得什麼、哪裡開始跟不上；同時保留有效場景與不希望修掉的特質。不要只列缺點，也不要把個人偏好寫成所有讀者的共識。
4. **形成可回應項目。** 每項給穩定 ID、具體位置或短引文、讀者感受、原因推測、可選方向與複讀觀察問題。分清文本事實、主觀感受、推測、待揭曉懸念及可核實矛盾。改善方向不是強制解法。
5. **交給創作者決定。** 創作者可採納、試寫、保留原意、延後或需要釐清；評論者不可代填創作者立場。未回應不等於同意，不因未採納而判作品不合格。
6. **有新文本才複讀。** 依實際修改檢查閱讀經驗是否改變，允許改善、部分改善、未改善、產生新代價、無法判斷；不以「作者照建議做了」作為改善證據。原評論和原判斷保留，新結果另存。

## 檔案與 ID

- 每輪使用 `YYYY-MM-DD-作品形態-NN/`，例如本輪的 `2026-10-29-novel-01/`。
- `review.md`：評論快照，包含閱讀範圍、整體評論、優點、疑慮、改善順序與限制。
- `response.md`：創作者回應及後續追蹤；項目 ID 不因排序或決定而重新編號。
- 有複讀才新增 `follow-up-YYYY-MM-DD-NN.md`，記錄前後版本與項目判斷，再更新回應表的複讀連結。
- 評論 ID 例如 `RF-20261029-01`；疑慮項目使用 `RF-20261029-01-F01`，優點使用 `RF-20261029-01-K01`。跨輪引用完整 ID。
- 新增評論或複讀後，更新本頁索引及對應回應表；不需要另建資料庫或自動化。
- 舊評論的事實誤讀可加日期勘誤，說明修正與受影響結論；不要悄悄重寫當時的閱讀經驗。

可直接複製：[評論範本](templates/review.md)、[創作者回應範本](templates/response.md)、[複讀範本](templates/follow-up.md)。複製後填實值，刪掉未使用提示；不要把範本占位文字發布成正式結論。

## 創作者決定與複讀結果

兩個欄位分開，避免把「同意改」當成「已改善」。

| 創作者決定 | 意義 |
|---|---|
| 待回應 | 尚未取得創作者的決定 |
| 採納 | 創作者同意處理；不代表已改稿 |
| 試寫 | 先做局部版本，再比較效果 |
| 保留原意 | 創作者理解感受，但選擇保留；可附理由 |
| 延後 | 目前不處理；可附預期處理時機 |
| 需要釐清 | 證據、意圖或方向仍需討論 |

複讀結果使用「未複讀／改善／部分改善／未改善／產生新代價／無法判斷」，並附文本位置與實際感受。一項可同時改善某部分、產生另一代價，須分別敘述。

## 評論邊界

評論是供創作者選擇的回饋，不是故事正典、設定變更或下一章指令。不要求主角永遠正確，不把角色的道德缺陷直接視為寫作缺陷；應檢查讀者是否能理解其動機、後果及作品呈現方式。未回收伏筆先記為期待或耐心風險，除非已有明確矛盾證據。避免只為提高評論分數而改稿；不設總分、必修率或固定通過門檻。
